The contract for the toolchain: the CLI surface, dev HMR and build-error reporting, the `hybrid`/`static` output modes, update notification and `puzzle upgrade`, interactive `puzzle init`, the `/testing` utilities, the `--fixtures` switch, the DevTools bridge, code splitting and production names, and `puzzle check`. ## 13. CLI tooling

Commands live in `compiler/cmd/puzzle`: `init`, `generate`, `add`, `dev`, `build`, `preview`, `check` (§63), `upgrade` (§41), `doctor`, `info`, `version` (also `--version` / `-v`; one template, `puzzle version <v>`, whose last field `upgrade` parses). The hidden `compile <file.pzl>` exists only for the §53 Vitest plugin.

- **Flag conventions.** Shorthands follow npm/gh/vite habit: `-p` port, `-t` template, `-m` mode, `-f` force, `-y` yes, `-q` quiet, `-o` open, `-v` version (never verbose). Overwrite is `--force` everywhere. `add --overwrite` and `init --dir` are hidden aliases that print no notice: a 0.9 `upgrade` re-execs the new binary with `add skills --overwrite`, so a deprecation notice would land in its output. `--yes` takes every prompt's default without asking (`init`, `add skills`, `upgrade`, `upgrade skills`). `--no-color` on every command sets `NO_COLOR`; it is read from argv before parsing, so usage errors are uncoloured too. `info --json` keys: `puzzle, platform, node (null if absent), projectRoot, sourceDir, outputDir, styles`; `doctor --json`: `dir, ok, failures, checks[{name, status: pass|fail|warn, detail}]`, same exit code. JSON keys are additive-only.
- **`build` flags.** `-m/--mode production|development` (default production), `--static`/`--hybrid` (§36), `--fixtures` (§54), `-q/--quiet` (drops the summary, the static/hybrid page report and the update notice; errors, warnings and skipped routes still print), `--profile-build`.
- **`dev` flags.** `-p/--port N` (default 3000, scans upward when busy — D90), `--strict-port`, `-o/--open`, `--fixtures`, `--profile-build`, and `--host` (shared with `preview`):
  - omitted → loopback (`127.0.0.1`, banner says `localhost`);
  - bare `--host` → every interface (`0.0.0.0`), and the banner adds a `Network:` URL per non-loopback IPv4 address;
  - `--host <ip>` → that address, but only when the token immediately after a bare `--host` is an IP literal (v4/v6) or `localhost`, even if a directory has that name;
  - `--host=<addr>` → that address, never overridden. Hostnames need the `=` form; a bare `--host` followed by a word that leaves too many positionals errors with `--host takes a hostname only as --host=<name>`.
  - pflag gives an optional value only to the `=` form, so `main()` rewrites `--host <ip>` to `--host=<ip>` before parsing (`normalizeHostArgs`, `cmd/puzzle/serveflags.go`; dev/preview only, nothing after `--`).
- **`--profile-build`** (or `PUZZLE_PROFILE_BUILD=1`) prints phase tables to stderr for the one-shot build and for dev startup and every rebuild in every mode (D156). It never changes stdout, artifacts, rebuild selection or failure behavior.
- **Version pair ([[DECISION-D202-CLI-RUNTIME-VERSION-PAIR]]).** The CLI and the project's installed `@magic-spells/puzzle` must be on the same side of a breaking release (a new minor while the major is 0, else a new major; a patch difference passes). `build` and `dev` stop on a mismatch, and also when no runtime is found (that message names `<pm> install` from the nearest lockfile). `check` (with or without `--fix`), every `generate` kind and `add piece` stop on a mismatch only, so they still run before an install. A `PUZZLE_RUNTIME` checkout and an app inside the Puzzle repo are never compared. `doctor` fails its runtime row with the same message; `preview`, `info`, `init`, `upgrade` and the other `add` kinds do not compare versions. The message (a CLI older than the project ends with `Or upgrade this CLI:` instead):
  ```
  This project has Puzzle 0.9.0 installed, and this CLI is 0.10.0.
    Use the project's own CLI:  npm run dev, npm run build, or npx puzzle <command>
    Or upgrade the project:     puzzle upgrade
  ```
- **`puzzle init [app-name|path] [-t default|static] [--typescript] [-y]`** scaffolds a Tailwind-first app (`app/` with `app/app.js`, or `app/app.ts` with `--typescript`; `puzzle.config.js`; `index.html`) from an embedded template tree. `default` is a single-page app; `static` is an `output: 'static'` site (Home, About and a 404 page), and its printed next steps add `npm run build` and `npm run preview`. The argument may be a path, create-vite style: `../apps/foo` creates `foo` inside `../apps`. The hidden `--dir` is the base a relative argument resolves against; an absolute argument plus `--dir` errors. Non-interactive on a non-TTY (no argument is an error); on a TTY it prompts for what flags left out (§42). The name must be npm-safe (lowercase letters, digits, hyphens, starting with a letter); a non-empty target directory is refused. The scaffolded `package.json` declares `"engines": { "node": ">=24" }` (D200) and a `"preview": "puzzle preview"` script. Every template also writes a test suite (D194): `vitest.config.js` (`plugins: [puzzle()]` from `/vitest`, `environment: 'jsdom'`), a `"test": "vitest run"` script, `vitest` + `jsdom` dev dependencies, and `tests/` (`default`: `Counter.test.js`; `static`: `Home.test.js`). `--typescript` writes `.test.ts` files and adds `tests/**/*.ts` to `tsconfig.json`'s `include`; `puzzle check` still covers `app/` only.
- **`puzzle compile <file.pzl>`** (hidden) prints one standalone ES module to stdout, compiled under the file's path from the project root as the build names it, so the D20 mode, the D59 scope id and diagnostics match the build. The script keeps its `.pzl` lines, a `lang="ts"` script is type-stripped with an inline source map back to the `.pzl`, `{#svg}` is inlined from the nearest `app/assets/`, `<style>` is dropped, and no bundler runs. Errors are `file:line:col: message` on stderr with exit 1; warnings go to stderr and the module still prints. Not a stable output format; `build` is the real compile.
- **`puzzle generate <component|view|layout|model> <Name> [--path <dir>] [-f/--force] [--family <Members>] [--dir <app-root>]`** (alias `g`) writes a stub into `app/components|views|layouts|models`, finding the root by walking up for `package.json`/`puzzle.config.js`. `.pzl` names are PascalCase, model names lowercase; `Component` is refused for every `.pzl` scaffold (D180). `--family` (components only) scaffolds a family directory plus an `index.js` barrel (D167). **A root `tsconfig.json` makes every stub TypeScript** (D54): `<script lang="ts">` with typed props and `data()`, `app/models/<name>.ts`, an `index.ts` barrel, and a model hint naming `app/models/index.ts`.
- **`puzzle add tailwind`** writes the canonical `puzzle.config.js` + `app/styles/styles.css` when absent.
- **`puzzle add piece <name…> [--registry <path|url|npm:pkg[@version]>] [--pieces-version <v>] [-f/--force] [--dir]`** copies pieces from the puzzle-pieces registry: resolves `registry.json`, pulls `registryDependencies` transitively (piece names and `lib/*.js` utils), copies files **verbatim** under each manifest's `targetDir` (default `app/components/ui/`; libs to `app/lib/`), and records sha256 hashes in `pieces.lock` (per file, keyed by the app-root-relative slash path). Existing files are refused unless `--force` — an all-or-nothing pre-flight. The registry theme is copied to `app/styles/pieces.css` when absent (locked like a piece). Registry source: `--registry` → `PUZZLE_PIECES_REGISTRY` → the `@magic-spells/puzzle-pieces` npm package at the newest release matching the CLI's major.minor (an older release, with a notice, only when no breaking release lies between it and the CLI, so below 1.0 a missing match is an error; `--pieces-version` pins exactly).
  - **Next steps are printed, never run:** the accumulated `npm install` line (when pieces declare different version floors for one dependency, D169, the highest wins; a bare name loses to any floor), the `@import './pieces.css';` advisory, one `@import "<spec>" layer(components);` line per stylesheet the resolved manifests list in `styles` (load order, first occurrence wins; the first goes after `@import "tailwindcss";`, each later one after the line before it), a stale-theme hint when an existing `pieces.css` differs from the registry's (lock-hash match → `puzzle add theme default`; else merge by hand or `--force`), and one `puzzle add theme <names…>` line for palettes the pieces' manifest `themes` name that the app has neither on disk nor imported from the package.
  - **Compound pieces (families).** A manifest `files` entry carrying a directory (`NavigationMenu/Item.pzl`) is copied path-preserving under `targetDir`. The directory in `files` is the only signal — no `family` field.
  - **Manifest paths must be clean** (`validateManifestPath`): slash-separated, relative, non-empty, no backslashes, no `.`/`..` or empty segments. Applies to `files`, `targetDir`, the registry `theme`, and `lib/` dependencies; the error names piece, field and entry and fires before any write. Rejecting rather than cleaning keeps the manifest entry, destination path and lock key one string.
- **`puzzle add theme [name…]`** (D171): with no names, lists the registry palettes and this app's install state (`installed · outdated` when bytes differ from the registry's). With names, copies each palette — the default one to `app/styles/pieces.css`, others to `app/styles/themes/<name>.css` — and locks it. A palette `styles.css` already imports from `@magic-spells/puzzle-pieces/themes/` is skipped. It never edits `styles.css`; the `@import` and `data-scheme` switch are printed. An unmodified older copy (still matching its lock hash) is refreshed; a locally modified one is refused without `--force`.
- **`puzzle add deploy [host] [--static|--hybrid] [-f/--force] [--dir]`** (D198): with no host, lists `vercel`, `netlify`, `cloudflare`, `nginx`, `apache`. With one, copies that host's embedded template from `deploy/` — `vercel.json`, `netlify.toml` and `nginx.conf` to the app root; Cloudflare's `_headers` and Apache's `.htaccess` to the public folder (`app/public/`, or `public/` when only that exists) so the build copies them into `dist/`. The template matches the output shape: SPA/`hybrid` fall back to the shell after real files, `static` serves `404.html` with a 404 status and never the shell; every template caches the content-hashed names (§59) for a year and leaves HTML revalidating. `--static`/`--hybrid` pick the shape, else the config's `output`. An existing file with other bytes is refused without `--force`; identical bytes are a no-op. Host-side steps and per-locale 404 lines (static, `i18n.routing: 'prefix'`) are printed, never written.
- **`puzzle add skills [-f/--force] [-y/--yes] [--skill-root <dir>…]`** (alias `skill`; D78) installs the CLI's `go:embed`ed agent skill into `<root>/skills/puzzle/` for each detected config dir (`~/.claude`, `~/.codex`, `~/.cursor`). TTY: checkbox multi-select, all pre-selected; non-TTY installs to all detected targets. No targets is a friendly exit 0. `--skill-root` (repeatable) pins the roots, skips the prompt, and must name existing dirs. Every install writes `<dest>/.puzzle-skill-version` (missing/blank reads as unknown). Existing destinations classify as: **missing** → install; **stamp matches** → skip as up to date; **stale/unstamped** → yes/no confirm (default yes) naming the version delta — declining skips only conflicts; **symlink** → one `!` line, never written through. On a non-TTY a stale destination refuses with the `--force` message (`--yes` accepts the refresh instead) and writes nothing; up-to-date is not a conflict, so the command is idempotent in CI. `--force` writes every selected target, symlinks included. A reinstall **replaces** the tree (removed, then copied) so dropped files cannot linger — except through a symlink, which is written in place.
- **`puzzle upgrade skills`** refreshes from this binary's embedded payload (no registry check, no re-exec). It refreshes only config dirs that already carry a skill, skips symlinked ones, prints the `--force` hint when all are current, and on a non-TTY installs without prompting — the command names the clobber.
- **`puzzle preview [dir] [-p/--port N] [--strict-port] [--host …]`** (D148) serves an existing `dist/` the way the production host will, by output mode: SPA → history fallback to the shell; `hybrid` → the route's prerendered page, else the shell; `static` → clean URLs (`/about` → `about/index.html`) and a real 404, never the shell — `dist/<first-segment>/404.html` when that folder (exact case) holds one (a locale's own 404, §36), else `404.html`. No watcher, SSE, reload injection or `dev.proxy`. Default port 4000 (so it can run beside `dev`) with the same scan. A missing/empty `dist/` is an error naming `puzzle build`. An explicit config `output` wins; otherwise the artifact's marker (`data-puzzle-static` / `data-puzzle-ssg` in `dist/index.html`) identifies the mode, and a config/artifact or app-entry-shape disagreement warns rather than guesses. URL→file resolution is one resolver (`compiler/internal/serve`) shared with `dev`.
- **`puzzle doctor [dir]`** — ✓/✘/! checks (node on PATH at version 24 or later per D200, the build entry by the rule below — both present fails — `index.html`, config loads, Tailwind CLI resolves, the runtime package with its installed version, failed with the version-pair message when that version is across a breaking release from the CLI); exit 1 on any failure. **`puzzle info [dir]`** prints version, platform, node version, project root, source/output dirs and the styles pipeline.

**The build entry (D54).** Every bundling path — `build` in all three modes, `dev` (SPA and static), the prerender passes, `--fixtures` — and `doctor` use one rule: `app/app.ts` when it exists, else `app/app.js`. Both present is a hard error naming both; neither is "entry point not found". `dev` re-resolves each rebuild and asks for a restart if the answer changed. Output is `dist/app.js`, or `dist/app-[hash].js` with production hashing (§59); `puzzle.config.js` stays JavaScript.

**No-JS-rewriting rule (D3).** `add` and `generate` never parse or rewrite user JavaScript: `generate model` does not edit `app/models/index.js`/`.ts`, `add tailwind` never rewrites an existing config, and `add piece`/`add theme` never edit `styles.css`, and `add deploy` writes whole template files only. When wiring is needed they print the exact snippet. Generated `.pzl` stubs are compile-checked in tests.

**Translations build (D175; template side is §66).** Only when `puzzle.config.js` declares `i18n`: `compiler/internal/locales` loads every configured `app/locales/<tag>.json`, validates with positioned errors (bad value type by key path, flatten collision, plural entry without `other`, `_` in a file name, a configured locale without a file), flattens nesting to dotted keys (plural entries stay objects), fills each locale's missing keys from `defaultLocale` (one warning per locale, plus one for keys only a non-default locale has), and writes minified sorted-key `dist/locales/<tag>.<HASH8>.json` (sha256 → base32, first 8) into staging before the passes. `locales/` is a reserved public output name while `i18n` is on. The manifest is the virtual module `@magic-spells/puzzle/i18n/manifest` (`{ defaultLocale, locales: { tag: 'locales/<tag>.<hash>.json' } }`, config order, plus `routing` and `detect: false` only when set), regenerated each rebuild; outside a Puzzle build it resolves to `null`. Warnings: `t` used without `i18n`; `app/locales/` without `i18n`; a literal `t('key')` missing from the default table (did-you-mean). Without `routing`, prerender renders in `defaultLocale`; every page carries `<script type="application/json" data-puzzle-locale="<tag>">` at the shell's `</body>` (static `prerender:false` pages too; a hybrid `prerender:false` page is the verbatim shell and fetches). SPA dev re-emits locale files on an `app/locales/**` edit, refreshes the manifest, rebuilds and reloads, pruning superseded hashed files after success; static dev treats a locale edit as render-wide (D155).

**Locale URL prefixes (D177).** `i18n: { …, routing: 'prefix', detect?: boolean }` and a top-level `site: 'https://example.com'`:

- `routing` accepts only `'prefix'`; `detect` must be a boolean and `detect: false` removes the first-visit redirect. Path routing only — the SPA throws in `mount()` under hash or memory mode, hybrid already rejects them, static ignores `routerMode`.
- `site` is an absolute http(s) origin with a host name and nothing else — a path, query, fragment or user info is an error pointing at `routerBase`; a trailing `/` is dropped. It makes `hreflang` alternates absolute and turns on the sitemap. Under prefix routing without `site` the build warns once (alternates stay root-relative).
- **Output:** every prerendered page is written once per locale, default locale at the dist root and each other locale under `dist/<locale>/` (§36).
- **Sitemap:** every prerendering build that sets `site` writes `dist/sitemap.xml` — every prerendered page except 404 and `prerender: false`, each entry carrying `xhtml:link` alternates under prefix routing. A `public/sitemap.xml` is kept, with a warning. Works without `i18n`.
- **Collisions are build errors:** a route whose first segment equals a non-default locale tag (case-insensitive), and a root-level `public/<locale>/`.
- **href warning:** under prefix routing a literal root-relative `href` on `<a>`/`<area>` warns (it would skip the prefix; use `link()`). Skipped: `//host`, dynamic values, `{#raw}`, and a last static segment with a file extension. The usage scan always collects them (`Usage.RootHrefs`); only prefix routing prints.

## 27. Dev HMR: state-preserving reload

`puzzle dev`'s reload preserves app state across rebuilds (D57). Zero production cost: every branch sits behind `__PUZZLE_DEV__`.

- **Reload + transplant, not module swap.** Each rebuild runs the fresh bundle via `location.reload()`. Just before, the injected SSE client calls `window.__PUZZLE_APP__.__devSnapshot()`, which writes a one-shot `sessionStorage` blob (`__puzzleHMR`). The rebooted app restores in two phases (§35): the store transplants after `beforeMount` and **before navigation #0** (so the first `data()` sees restored records), then view-local state restores once the chain has mounted.
- **What survives:** store contents (the `_persist()` wire shape, hydrated validation-exempt in identity-preserving replace mode, so the snapshot beats configured `storage` on pk conflicts), §61 read state, each mounted view's **state layer only** (`setState` + `created()` state, through a JSON-safe walk that drops functions and DOM nodes — `data()`-derived values are recomputed, never snapshotted), the URL, and scroll (§14).
- **View identity** is `${class name}:${per-class mount index}` — deterministic because the same URL mounts the same chain in order. A mismatch cold-starts that view. The edited component's own state is restored too; a shape mismatch self-heals on the next edit.
- **Bounds:** one-shot (deleted on read), expires after 10 s so a manual F5 cold-starts; memory mode is exempt; focus/selection are lost; DOM islands (§17) re-seed. Every restore step is fail-soft — never a crash.

## 36. Static output — `output: 'hybrid' | 'static'`

Two build modes that prerender every static route to its own HTML file. No SSR server and no hydration protocol; compiled `.pzl` output is environment-agnostic ViewNode data. Both share one serializer, one prerender orchestrator and one chain assembler (`client-runtime/ssg/assemble.js`).

- **`hybrid`**: prerendered pages **plus** the shared SPA bundle; the router replaces the prerendered DOM at navigation #0 and the site is the SPA thereafter.
- **`static`** (D81): true static pages — **no router, no takeover, no history API**, no `app.js` in `dist/`. Navigation is plain page loads; each page ships a per-page module that mounts only its own components.

**Activation:** `--static` / `--hybrid`, or `output: 'static' | 'hybrid'` in `puzzle.config.js` (any other value is a config error). The flags are mutually exclusive and must agree with the config. No `output` means SPA.

**Dev serving (D148/D154).** `puzzle dev` runs the SPA loop for plain and `hybrid` projects (dev prerenders nothing for hybrid). An `output: 'static'` project gets the real pipeline on every rebuild (bundle + Tailwind + prerender + per-page modules) into staging with an atomic swap, so a failed compile or prerender keeps the last good pages serving, with static-host semantics — clean URLs, full-page navigations, a real 404 (`dist/<first-segment>/404.html` when that folder holds one, else `404.html`, else a minimal dev 404). The reload client is injected at **serve time** into every HTML page (`dist/` stays production-clean), so reload and the §50 overlay reach static pages, and a 404 self-heals when its route appears. The artifact is byte-identical to `puzzle build --static --mode development`. `--fixtures` is rejected (§54). Verify either mode's artifact with `puzzle build` + `puzzle preview`.

**Prerender pipeline.** After the normal bundle + Tailwind + `public/` copy into staging, the CLI bundles a node-platform entry (same `.pzl` plugin, `__PUZZLE_DEV__=false`, `__PUZZLE_TAKEOVER__=false`) that imports the app entry's **default-exported PuzzleApp** (`export default app` is required) plus `@magic-spells/puzzle/ssg`, and runs it under `node` once. A prerender failure fails the build; the staging swap keeps the last good `dist/`. The summary (pages, skipped routes, warnings) rides the `__PUZZLE_SSG_JSON__` stdout sentinel.

**Output paths.** Directory-style in both modes: `/` → `dist/index.html`, `/components/badge` → `dist/components/badge/index.html`. Each page is the shell with the rendered markup injected into the required empty `#id`-form `config.target` and the first `<title>` replaced by the route's resolved `meta.title` (§45). Pages link absolute paths. **A page may not overwrite a copied `public/` asset** (D126) — a collision is a build error naming route and asset; the one exemption is `/` writing `index.html`, the shell itself. Separately, `app.js`, `app.js.map` and `styles.css` are reserved root-level public names (files only, root only, case-insensitive).

**Per-locale pages (D177).** Under `i18n.routing: 'prefix'` (§13) every route is prerendered once per locale, default first: the default locale's pages at the paths above, every other locale's under `dist/<locale>/…` (`dist/es/about/index.html`, the catch-all at `dist/es/404.html`). Each page has its own `<html lang>`/`dir`, carries only its own locale's table island, renders with its own format locale, and gets the `hreflang` alternates (§45 in DOC-SPEC-ROUTER). `config.beforeMount`'s facade gains `locale`, since it runs once per locale. Static pages of one route share one slug and one page module. Default-locale pages (404 included) also carry the inline first-visit redirect script (`ssg/redirect.js`) unless `i18n.detect: false`; `prerender: false` pages get neither alternates nor the redirect. HTML output multiplies by the locale count; JS, CSS, locale files and assets do not.

**Parameterised routes (D179).** A leaf `:param` route may declare `staticPaths` (route field, DOC-SPEC-ROUTER): an array of params objects, a function (sync or async; given `{ store, config, locale? }`, run after `beforeMount`, once per locale pass) returning one, or a model name (one page per record, each param from the record's same-named field). Each entry is one page, rendered like a fixed route with those params; every value must be one servable path segment. Static: all pages of the route share one page module and carry a `data-puzzle-static-route` island (path + params) the kernel reads instead of `location`; an unlisted value is a 404. Hybrid: an unlisted value is served by the SPA, and a generated path an earlier route matches first is skipped (`shadowed`). Errors, warnings, collisions and locale interplay are in [[DECISION-D179-STATIC-PATHS]].

**Render semantics** (`client-runtime/ssg/`). Each route's layout + view chain is assembled and loaded via `preload()` — `created()` + awaited `data()` with `this.route` populated, `lazy()` positions (§62) awaited first — so **no `mounted()`, animations or DOM** run at build time; `data()` runs once per page under Node (module-scope browser globals must be guarded). `render()` always, never `renderSkeleton()`. The serializer mirrors the ViewManager: same `expandSlots`, `@event`/`key`/`island`/`ref`/`flip` dropped, boolean props as bare attrs, `{#svg}` seeds verbatim, scoped-style stamps kept. Principled differences: `value` serializes as an attribute; `<script>`/`<style>` are RAWTEXT (D113) — never entity-escaped; JSON-typed scripts (`application/json` or `+json`) emit `<` as its JSON unicode escape (breakout-proof, like the data islands); other script/style content is raw, and the build **fails** on `</script`/`</style` (case-insensitive) or the `<!--` + `<script` pair. `config.beforeMount` is awaited once with a `{ store, config }` facade — build-time only in both modes.

**Hybrid takeover (router).** The target is stamped `data-puzzle-ssg`; pages link the emitted SPA entry and stylesheet names (§59). On navigation #0 a marked mount container is cleared (`replaceChildren`) inside the commit window after the data gate, the marker removed, and the incoming top view's enter suppressed (`skipEnter()`) — no flash, no duplication. If the mount rejects, a configured `errorView` renders first (§60) and the prerendered content stays cleared; the snapshotted prerendered nodes and marker are restored exactly (D140) only when no `errorView` is configured or it also failed, so the next mount re-runs the takeover clear.

**Static pages (per-page modules, D81).** The target is stamped `data-puzzle-static`. Codegen stamps each class with `Class.__pzlModule` (app-relative source path); `compiler/internal/build/prerender_pages.go` emits one ES module per page, `dist/_puzzle/<slug>.js` (`<slug>-[hash].js` with production hashing, §59; `/`→`index`, `*`→`404`, else `/`→`--`, collisions `-2`, `-3`…), importing `mountStatic` from `@magic-spells/puzzle/static` plus exactly that page's classes (a `lazy()` position contributes its **resolved** class). esbuild splitting factors shared code into `dist/_puzzle/chunks/`. Each page's store is serialized into `<script type="application/json" data-puzzle-static-data>` (plus the §61 read-state island); the shell's `/app.js` tag becomes the page module and `staging/app.js` is dropped. `mountStatic` wires the build-time ctx (Store + function registry; `ctx.router` is a link stub — `url()`/`current` work, every navigation method throws), rehydrates the islands (replace mode), assembles and preloads via `assembleChain`, `skipEnter()`s the whole chain plus its nested components on a marked page (the markup is already on screen), then `replaceChildren()` + mounts over identical markup; an unmarked `prerender: false` page is a first paint: it sets its route title (the shell's `<title>` is verbatim) and follows the router's initial-navigation rule — the topmost view plays in, the layout and deeper views `skipEnter()`, nested components enter normally. On a marked page a rejected mount restores the prerendered nodes and destroys the failed root (D140). The stub's mode is **always path-shaped**: `routerMode` is ignored with a build warning (a hash href is a dead link on a static file); `routerBase` applies.
- Models load from `app/models/index.js|ts` and app functions from `app/functions.js|ts` when present (a leftover `app/formatters.js|ts` warns, naming the rename, D199); models or functions registered only in the app entry warn (build-time only, missing client-side).
- **The adapter capability (D157/D158) is bound by identity.** The bare capability is re-imported from `@magic-spells/puzzle/adapter`; a configured one that is the default export of `app/adapter.js|ts` is imported from there (the prerender checks the module equals `config.adapter`, else bypasses it); a capability configured inline in the app entry makes the page module import the app entry and read `app.config.adapter`, with `app.mount()` inert for that pass (`__PUZZLE_CAPTURE__`). The inline form works but costs page weight and prints an advisory naming `app/adapter.js` — never an error.

**Route matching (all modes):** a single trailing `/` is not significant (`/docs/` matches `/docs`; a `:param` never swallows it), since static hosts serve directory URLs.

**404.** The top-level catch-all (`path: '*'`) renders to `dist/404.html` with the same treatment (`prerender: false` on its chain writes the plain shell); under prefix routing each other locale's to `dist/<locale>/404.html`. No catch-all → an advisory warning. In hybrid the live router also serves it for unmatched paths; in static the file is all there is. The `init` templates ship a `NotFound.pzl` catch-all.

**Boundaries.** A `:param` route without `staticPaths`, or with an empty list, is skipped with a warning naming the field, in both modes. `prerender: false` anywhere in a chain writes the plain shell at that path — an SPA island in hybrid, a client-rendered island (data island + entry module, no marker) in static. Not supported: DOM-adoption hydration, a zero-JS static opt-out, link prefetch in static pages (§69 rides the SPA router, so hybrid has it after takeover), and flat `name.html` output.

## 41. CLI update notification + `puzzle upgrade`

The CLI reports newer releases and upgrades the global CLI and this project through the user's package manager (D76). npm owns installation; the binary never replaces its own files.

**Passive notice (`build`, `dev`).**
- One dim line — `✨ puzzle <latest> available (current <v>) — run puzzle upgrade` — after the build summary (suppressed by `build -q`), or from `dev`'s `OnReady` hook after the ready banner.
- **Skipped entirely** when `CI` or `PUZZLE_NO_UPDATE_CHECK` is non-empty or stdout is not a terminal; the gates run first, so scripted runs never touch the network.
- **Never waits on the network.** `CheckPassive` reads the cache `<os.UserCacheDir()>/puzzle/update-check.json` (`checked_at` RFC3339, `latest`, optional `failed_at`; TTL **1 hour**; atomic temp-file + rename writes, retried on Windows sharing violations).
- A stale or missing answer spawns a **detached refresh** for the next run: `os.Executable()` re-exec'd as the hidden **`puzzle update-check`** (3 s timeout; writes the cache or `failed_at`; prints nothing; exits 0) with null stdio, its own session (`Setsid`; `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP` on Windows) and a reaping `Wait()` goroutine. A process, not a goroutine, because `build` exits too fast. A failed spawn is silent; the helper re-checks the gates and never spawns another helper.
- **Failure backoff 15 minutes:** a failed refresh stamps `failed_at` (leaving `latest`/`checked_at`); no helper spawns until it expires; success clears it.
- Endpoint: `GET <registry>/@magic-spells/puzzle/latest` with `Accept: application/json` — never the abbreviated install-v1 format, which 406s on version endpoints. `<registry>` defaults to `https://registry.npmjs.org`; `PUZZLE_REGISTRY` overrides.

**`puzzle upgrade [--check] [-y]`.**
- Fetches latest synchronously (5 s; failure is an error), then prints one row per scope: `the global CLI` / `this project`, `<old> → <latest>` or `<v>, up to date`, then the project's full path and the manager (`  this project    0.9.0 → 0.10.0  /Users/you/my-app (npm)`). A declared project with nothing installed shows `<range> (not installed) → <latest>` and counts as behind. A running binary that is neither scope first prints `✨ puzzle <latest> available (current <v>)` when it is behind. When nothing is behind, the only line is `✓ puzzle <v> is up to date`, with `(the global CLI and this project)` naming the scopes that exist; `<v>` is latest then, or the running binary's version when there is no scope. `--check` prints the rows (and the ✨ line) and changes nothing.
- **Scopes.** The global CLI is the running binary when it is the global install, else a puzzle package in the `npm root -g` / `pnpm root -g` folder (memoized with detection's queries). None installed is no scope; the command never installs one. This project is the nearest `package.json` at or above the cwd, no higher than home, when it parses and its `dependencies` or `devDependencies` name the CLI; a nearer one that does not, or does not parse, means no project. A project takes its manager from the first lockfile, and its installed copy from the first `node_modules/@magic-spells/puzzle`, at or above it, so a workspace member reads the root's. Its install runs in its own folder.
- **The running binary's install context is a property of the executable, never of the cwd.** The cwd decides only the project scope. A global binary is the global scope. A project binary is the project scope, and the cwd is not searched. A workspace or nested binary takes the project's place: no project row, and the cwd is not searched. Any other binary is neither scope.
- Resolve `os.Executable()` through symlinks, then take the **nearest ancestor `node_modules` that actually contains `@magic-spells/puzzle`** (nearest, not outermost, so a hoisted copy is never mistaken for this one); its parent is the owner. Every branch names the owner or explains — **nothing falls through to `npm install -g`**:
  - **Explains when behind (not on `--check`), exit 0, and the remaining scopes are still offered:** no `node_modules` above the binary (a source build → clone-and-`go build` instructions; `go install …@version` cannot work because of the puzzle-lang `replace`); an npx/`dlx`/`bunx-*` runner cache (→ `npx @magic-spells/puzzle@<latest>`); a copy nested in another package's `node_modules`; a workspace root (`workspaces` field, or `pnpm-workspace.yaml`, `lerna.json`, `nx.json` or `rush.json`) that doesn't declare the CLI (→ `npm install …@<latest> -w <member>`).
  - **pnpm-global** — the owner has pnpm's global-root shape `<pnpm home>/global/<n>`, or pnpm reports it as its global root → `pnpm add -g`. Checked before the project test, because pnpm's global root is itself a package declaring every global install; the full shape is required so `~/pnpm/app` is not misread.
  - **Project** — the owner's `package.json` declares `@magic-spells/puzzle` (any dependency field), or has a lockfile beside an undeclared local install (`--no-save`) → package manager from the first lockfile at or above the owner (`pnpm-lock.yaml`, `yarn.lock`, `bun.lock`/`bun.lockb`, else npm), dependency field preserved, run in that directory.
  - **Global** — only when npm or pnpm itself reports this `node_modules` as its global root → `npm install -g` / `pnpm add -g`.
  - Anything else (including `node_modules` with no puzzle package in any) → a `!` line naming where it looked (exit 0; the scopes are still offered).
- **Asking.** On a TTY there is one yes/no (default yes) per scope that is behind, all before any install: `Upgrade the global CLI?`, `Upgrade this project in <path>?`. A project crossing a release that may break (a new minor while the major is 0, else a new major) adds `<old> → <latest> may have breaking changes`. `--yes` upgrades every scope that is behind, after the rows print. A non-TTY upgrades only the scope the running binary is (none when it is neither) and prints `! To upgrade <scope>, run <command>[ in <path>]` for each other scope that is behind.
- Installs the exact fetched version, streams child output, propagates a non-zero exit naming the command. Platform binaries follow as exact-pinned `optionalDependencies`. A failed scope does not stop the other; the errors are joined into the exit, each naming its scope (`upgrading this project: …`).
- **Success is confirmed**: the copy is read back through the same lookup as before the install (an unusual global layout falls back to walking up from the binary) and must report the target. Then `✓ upgraded the global CLI <old> → <new>` or `✓ upgraded this project <old> → <new>` prints, `<old>` being the version read from disk before (or the declared range), and the update cache is written. A project upgrade across a breaking release adds one `!` line naming the installed copy's `CHANGELOG.md` ("Upgrading across versions") and `npx puzzle check --fix`.

**Agent-skill refresh** (after at least one scope is upgraded; D78):
- A target qualifies only when `<root>/skills/puzzle/` already exists as a real directory under a detected config dir. None is a silent no-op; a symlinked one gets one `!` line.
- `--yes` refreshes without asking. TTY: yes/no confirm (default yes) listing destinations. Non-TTY: one `!` hint naming them plus `puzzle upgrade skills`, no writes.
- The refresh **re-execs the newly installed binary** (the running one embeds the old skill). Candidates come from each scope just upgraded, global first, starting from the copy the read-back confirmed: the platform binary beside it (where a local install hoists it, and where pnpm, local or `-g`, links it beside the store copy the symlink leads to); the platform binary nested in the copy's own `node_modules` (npm -g); then `node_modules/.bin/puzzle` for a project, or the `PATH` `puzzle` and the running executable for a global. When only the project moved, its binary is the source. Each must answer `--version` with exactly the target, else the manual command is printed. The child runs `add skills --force --skill-root <root>…`. Nothing here fails the upgrade.

Semver comparison is a minimal in-repo `x.y.z[-pre]` implementation (SemVer §11 prerelease ordering); no new Go dependencies.

## 50. Dev build-error reporting

A failed `puzzle dev` build is shown **in the browser** as well as the terminal (D92). Dev server only.

- **Typed SSE events:** `reload`, `builderror`, `clear`. Client buffers are size-1, non-blocking and **last-write-wins**. Payloads are JSON-encoded, since SSE `data:` cannot carry raw newlines.
- **`builderror` is never debounced** — the D27 reload coalescing does not apply to errors.
- **Retained state.** The server holds the current error and replays it on connect. The SSE handler registers with the hub **before** reading it, so a racing transition can duplicate a frame but never drop one.
- **First-run shell.** When the index would 404 and an error is retained, the server answers **503** with a self-contained page: the escaped diagnostic rendered server-side, the reload client injected (self-heals on the next good build), and the overlay node adopted by id so the replay does not stack a second overlay. Without a retained error the 404 path is unchanged.
- Diagnostics (positioned `.pzl` errors, esbuild messages) pass through verbatim.

## 55. The DevTools bridge and wire protocol

The Chrome extension lives at `packages/puzzle-devtools` (D162); the framework ships only a **dev-only runtime bridge** (D100), and this section is the contract between them. Zero config surface, zero production bytes: the extension injects `window.__PUZZLE_DEVTOOLS_HOOK__` at `document_start` and the bridge registers into it when present. No hook → every touchpoint is a no-op; production → the bridge is DCE'd (`__PUZZLE_DEV__`, pinned by a build test).

**Envelope:** `{ puzzle: 1, v: <protocolVersion>, type, payload }`, protocol version 1, exchanged in `hello`; the extension must show a mismatch state rather than misrender.

**Events (runtime → extension, `hook.emit`):** `hello { protocolVersion, frameworkVersion }` · `app-mounted` / `app-unmounted` · `view-mounted { id, name, module }` / `view-destroyed { id }` · `flush { keys, notified }` (one per store flush batch) · `route-commit { pathname, query, params, chain, title }` (post-mount, pre-paint) · `perf-warning { kind, viewId, name, detail, count }` (only when a §56 guard trips).

There is **no per-render event**: the page hook buffers 500 pre-attach messages and the panel ring holds 200, so a render firehose would evict everything else. Render data is pulled via `snapshot:profile` while recording.

**Requests (extension → runtime, `hook.onRequest`):** `snapshot:views` (recursive `{ id, name, module, children }`, roots found by walking live views' vnode trees, never router internals) · `inspect:view { id }` → `{ name, module, params, props, shared, model, local }` with model and `setState()` layers separate, JSON-safe · `snapshot:records { type? }` · `snapshot:subscriptions` → `{ byKey, byView, held }` (function subscribers merged as `'fn'`; `held` lists keys a prepared-but-uncommitted `data()` run added, D146, also present in `byKey`/`byView`) · `snapshot:route` → `{ path, pathname, query, hash, params, route, routes, chain, title }` (patterns and view names, never live objects) · `edit:record { type, id, patch }` through the real `record.update()` (§20 applies; a throw returns `{ error }`) · `highlight:view { id, on }` · `log:view` / `log:record` (binds `window.$p`) · `perf:start` / `perf:stop` → `{ ok: true }` · `snapshot:profile` → `{ recording, durationMs, totals, views[], flushes[], warnings[] }`.

**Additive growth without a version bump:** unknown events fall into the extension's ring and unknown requests fail per call with `{ error }`. A `PROTOCOL_VERSION` bump forces every published app into `MISMATCH`.

**Profile aggregation lives in the bridge**, not the §56 collector, so rows carry bridge view ids and a recording retains no view references. **Identity:** view ids are session-scoped integers (WeakMap); `name` is the class name (dev builds are unminified); `module` is the `__pzlModule` stamp. `FRAMEWORK_VERSION` in `client-runtime/devtools.js` is a literal `release:prep` asserts.

## 56. Dev-only runtime performance profiling + render assertions

Development builds instrument render/data/Store through one collector, `client-runtime/devperf.js` (D121). **Production contains zero bytes of it**: class-method call sites use the inline `typeof __PUZZLE_DEV__ === 'undefined' || __PUZZLE_DEV__` probe (module-scope functions may use an equivalent constant) so esbuild folding removes every importer. No profiler state lives on PuzzleView, ViewManager, Store or Router — identity, counters, causes and windows are collector WeakMaps. The regression oracle is attribution: the production metafile attributes zero `bytesInOutput` to `devperf.js` and the bundle carries no profiler sentinel or bridge request strings.

- A render record is one `ViewManager.render` entry, timing the tree build separately from diff/patch; its mutation delta counts text/property/attribute writes and node insert/remove/move. Delta zero is a **wasted render**. Refresh requests are not renders.
- `data()` records wall time and sync/async shape. Component reuse records shallow-props bailouts vs data reruns; slot-only updates and `memo()` hits/misses are attributed per view/key. Store flushes record time, pending keys and unique notified subscribers. Serialized async `data()` records each head-of-line deferral and wait.
- A causal token follows store write/flush → refresh → render → work those schedule; per-view depth resets only when the chain is quiescent. Two deliberately asymmetric loop guards:
  - **Recursive, per chain — stops.** At 100 executions of one view in one non-quiescent chain, `console.error` and suppress its further renders in that chain.
  - **Cross-frame, rolling one second — warns only.** ≥ 60 renders in a second with ≥ 90% zero-mutation and no animation/morph cause → `console.warn`. It **must not** suppress: ordinary navigation reaches that rate (a route ancestor renders `depth + 2` times per navigation), and suppressing would stop a routed child mounting. A dev instrument may not change app behavior.
- The collector exposes temporary event sinks for §53's `measureRenders`; no test framework is imported.

## 59. SPA code splitting and production names — `build.splitting`, `build.hashNames`

`build: { splitting: true }` builds the SPA bundle with esbuild splitting: each dynamic `import()` becomes a lazy chunk under `dist/chunks/` ([[DECISION-D160-SPA-CODE-SPLITTING]]). Splitting is opt-in; absent/null is off and a non-boolean is a config error naming the key.

- **Production names ([[DECISION-D181-HASHED-OUTPUT-NAMES-AND-MODULEPRELOAD]]).** `build.hashNames` is a boolean; absent/null means **on** in production, whatever `build.splitting` says. `false` keeps fixed names (even when splitting); explicit `true` is strict (below). Development never hashes or adds preloads.
- **Hashed outputs.** SPA/hybrid entries use `app-[hash].js` (and its optional linked map); JavaScript-imported CSS uses `app-[hash].css`. esbuild owns their hashes and sourceMappingURL. The composed stylesheet uses `styles-<ContentHash>.css`, with the locale tables' SHA-256/base32 first-eight format. Without hashing, compiler outputs keep their fixed names.
- **Minified `<style>` blocks.** A production build minifies the collected `<style>` blocks with esbuild's CSS minifier before composing them after the Tailwind layer (which the Tailwind CLI already minified), and hashes the result. esbuild gets no browser targets, so vendor-prefixed duplicates such as `-webkit-backdrop-filter` survive; a targetless lightningcss pass would drop them. Development keeps the blocks verbatim.
- **Unlinked entry CSS.** When the entry emits CSS but no public HTML page references `app.css`, an SPA or hybrid build warns with the emitted filename and the exact `<link href="/app.css" rel="stylesheet">` to add to `app/public/index.html`. The SPA/hybrid dev watch builder prints this warning at most once per session. Static output links page CSS itself (below).
- **Shell rewriting.** After copying public assets into staging, the build rewrites src/href on script/link start tags referencing fixed compiler filenames (`app.js`, `app.css`, `styles.css`), with bare, `./`, `/` or deployment-base prefixes after removing query/fragment. Prefixes, query and fragment survive. Copied public files take precedence, including under a deployment base, and a relative reference resolves against its own page's directory first; remote references stay unchanged.
- **Default (unset) is lenient — hashing never fails a build or ships a dangling link.** Before bundling the build reads `public/`: the entry keeps `app.js` when `public/index.html` has no `<script src>` loading it, or when any other `public/**/*.html` page names `app.js`/`app.css` by its fixed name; the stylesheet keeps `styles.css` when the shell has no script/link tag referencing it or another public page names it. Each fallback prints one `warning: build.hashNames: <reason>, so <file> keeps its fixed name; …` line naming the page (a missing shell falls back for both); the styles warning is skipped when the stylesheet is empty. A shell reference to a compiler output that was not emitted is left as written.
- **Explicit `true` is strict.** A SPA/hybrid build requires `public/index.html` with a script reference to `app.js` (failure points at `build.hashNames: false`, before the swap); other public HTML pages are rewritten to the hashed names too; the stylesheet is hashed even when nothing links it; and a fixed compiler-asset reference with no emitted output is a build error.
- **Modulepreload.** Every production splitting pass preloads its entry's transitive static-import chunk closure, breadth-first in metafile import order and de-duplicated. Only non-external import-statement edges qualify; dynamic/lazy chunks are never preloaded. SPA/hybrid URLs inherit the entry's prefix and verbatim crossorigin; an unhashed shell without a recognized entry skips preloads. Links go on their own lines before the closing head at its indentation; a missing `</head>` fails a rewrite only when there are preloads to insert.
- **Static pages.** Static mode disables splitting/hashing for the discarded SPA pass. Its per-page pass always splits and therefore every production page gets preloads, independent of hashNames. Page modules become `_puzzle/<slug>-[hash].js` whenever hashing is on (the default); every locale/generated page sharing an entry is rewritten after bundling, retaining its module tag's routerBase prefix. The discarded SPA script is stripped under the normalized routerBase or an unprefixed spelling, including query/fragment suffixes. The JS summary still reports `_puzzle/<slug>.js`.
- **Page CSS (static).** A view, layout or component script may `import './x.css'`. esbuild writes one sheet per page entry holding the CSS of that page's whole graph, `_puzzle/<slug>.css` (`_puzzle/<slug>-[hash].css` exactly when the page module is hashed), and each page sharing that entry (every locale, every `staticPaths` page, `prerender: false` pages) gets `<link rel="stylesheet">` to it just before `</head>`, after the shell's global stylesheet, so page CSS wins cascade ties. Development links it too, under its fixed name and without preloads, in the one-shot build and in `puzzle dev` (whose partial render reuses pages that already carry the link). CSS reached only through a dynamic `import()` is part of the importing page's sheet and so loads with the page; the separate sheet esbuild writes for the lazy chunk is never loaded and is deleted. `dist/app.css`, the discarded SPA pass's copy of all imported CSS, ships only when a public page links `/app.css`; otherwise it is deleted, and each CSS file the app entry's graph imports that no page graph reaches (a CSS import in `app.js`, say) is named in one `warning: <file> is imported outside every page's views and layouts, so no static page loads it; …` line (by `puzzle build` on every run, and once per `puzzle dev` session). A shell that links `/app.css` in static mode makes every page load all imported CSS plus its own sheet, so a static app should not link it. An author's own `public/app.css` is a public file and always ships, over the compiler's copy.
- **Public assets** are copied verbatim, never hashed. Fixed root output names remain reserved; `chunks/` is additionally reserved only while SPA splitting is on.
- **Native ESM** has no chunk-loader runtime. Authors choose split points with `import()`; static imports remain eager.
- **Development** splits/prunes only when configured: the builder deletes only previous outputs it wrote that this pass no longer emits. Its fixed entry/CSS names and HTML stay unchanged.
- **Size banner:** per-dependency emitted bytes (metafile `bytesInOutput`, grouped by innermost `node_modules` package; the rest is app), with production warnings above 200 KB naming `import()` + `build.splitting`. App code and framework runtime are never advised.
- Route-level laziness is `lazy()` (§62), an ordinary consumer: its `import()` becomes a chunk with splitting and is inlined otherwise.

## 63. `puzzle check`: type-checking `.pzl` with the app's own tsc

`puzzle check [dir]` type-checks `.pzl` script bodies **and** template expressions and reports each diagnostic at its authored `.pzl` line:column ([[DECISION-D165-PUZZLE-CHECK]]). Opt-in: `build`/`dev` stay transpile-only.

```
$ puzzle check
app/components/TodoItem.pzl:11:16: Property 'remov' does not exist on type '{ toggle: (event: Event) => void; remove: (event: Event) => void; }'. Did you mean 'remove'?
```

- **The upgrade pass runs first ([[DECISION-D199-UPGRADE-PASS]]).** Before it type-checks, `puzzle check` looks through `app/` and `tests/` (`.pzl`, `.js`, `.mjs`, `.ts`; not `node_modules`, dotted files and folders, the public folder or `.d.ts` files) for code written for an older Puzzle: a bare `<Slot/>` outlet, `this.setData(`, a positional `data(params, props)` or `share(params, props)`, and the `formatters` config key or `app/formatters.js|ts`. A plain run lists each site as `file:line:col  old → new` and exits 1 before the type check. `puzzle check --fix` rewrites them, then type-checks: a bare `<Slot/>` becomes `<Outlet/>` under `app/layouts/` and `app/views/` and `<Children/>` elsewhere, and `app/formatters.js|ts` moves to `app/functions.js|ts` with its imports. With no TypeScript installed, `--fix` skips the type check and exits 0. A site it cannot rewrite safely is listed for the author to finish. Before the pass, the version pair (§13) stops a CLI that is across a breaking release from the installed Puzzle, so nothing is rewritten for the wrong runtime.
- **The app's TypeScript does the checking, and it must be TypeScript 7 or later.** It runs `node <dir>/node_modules/typescript/bin/tsc --noEmit --pretty false -p .puzzle/check`, where `<dir>` is the app or the nearest parent folder with that file (a workspace root's hoisted install counts) — the same on every OS, no shell. Puzzle never installs or links a compiler. `tsc --version` is read first; an older compiler stops the run before anything is generated: `puzzle check needs TypeScript 7 or later, found 5.9.3: npm install -D typescript@latest`. Other messages: `puzzle check needs TypeScript: npm install -D typescript`; `puzzle check needs Node.js on PATH: it runs the app's TypeScript compiler`; a directory with no `app/` is "not a Puzzle project", reported first.
- **Virtual files under `.puzzle/check/`** mirror the `.pzl` files under `app/` that the upgrade pass reads (dotted files and folders, such as an editor's `.#Home.pzl` lock link, `node_modules` and the public folder are skipped), rebuilt from scratch each run. A `lang="ts"` component emits one `.pzl.ts`: its script bytes verbatim, then a never-executed function re-stating every template expression as typed statements, lowered from the same expression tree the build compiles (D176). `{#if}`/`{#case}` become `if`/`switch`; `{#for}` becomes a declared visitor whose item type is destructured from the collection; a standard function call goes through `__puzzle_fn.name(…)` and is checked against its signature; any other bare call (an app-registered function) goes through `__puzzle_app_fn("name")(…)`, declared `(name: string) => (...args: any[]) => any` so it checks under `noUncheckedIndexedAccess`; a method is checked as the JavaScript method; each `@event` binding is assigned to a handler-typed const. The author's spelling is kept where the runtime adds safety — no inserted `?.` and no `?? {}` on `Object.keys`/`values`/`entries` (TS flags a never-nullish `??`). The shim references the ES2016–ES2023 string/array/object libs the method table needs. The root tag's attributes and the `<puzzle-skeleton>` body are checked too.
- **A JavaScript component emits a pair:** an unchecked `.pzl.script.js` mirror plus the checked `.pzl.ts` template wrapper; JS is never promoted into `checkJs`. **JS handler arity is not checked** — handler parameters are whatever TS infers from untyped JS, so `@click={ play(event) }` against `play: () => {}` is not an error. Handler **names** are checked against the keys of the `events` field, so a misspelled handler is reported — and so is one attached at runtime (`this.events.play = …` in the constructor or `created()`). With no `events` field there are no names, so every template handler is reported. Argument expressions are still checked; `lang="ts"` handler calls are fully checked.
- **Positions are byte-exact.** Each virtual file has a `.segments.json` sidecar pairing emitted and source ranges; scaffolding carries no segment. Remapping uses the run's in-memory tables, never a re-read, so a save mid-run cannot shift a position. Unmappable diagnostics pass through unrewritten.
- **The generated tsconfig extends the app's** when present, overriding what breaks the workspace (`rootDir`, `composite: false`, `skipLibCheck: true`, `noUnusedLocals/Parameters: false`), spelling `include` extensions out, and forcing `exclude: []`. It clears `baseUrl` (removed in TypeScript 7) and `moduleResolution` (TypeScript 7 removed its `node10` setting), and resolves the `@/*` alias from the config's own directory; the app's `module` and `allowSyntheticDefaultImports` apply as written. `paths` is always written, never inherited: the app's entries are merged with targets rewritten to resolve from `.puzzle/check/` (its `extends` chain is not followed), and `@/*` wins a clash as in the build. With no app tsconfig: `target: ES2020`, `module: ESNext`, `strict` and `noImplicitAny` off (TS 7 would otherwise default strict on).
- **Scope.** Template data is untyped: the wrapper's `__d` is `any`, because a template reads what `data()` returns, not the class's declared fields. A misspelled or mistyped data read (`{ user.nmae }`) is not reported, and neither is a `<Component is>` selector's data or module read, which reads like data. `Object.values` and `Object.entries` over data give `any` values. What the template check catches is a handler missing from `events`; a `lang="ts"` handler call or a standard-function call with the wrong number of arguments, or with an argument of a known type that does not fit; and a method or property that a typed value lacks — a literal, a standard-function result, an `Object.keys` result, a range-loop counter — including inside a selector (`cards[round(kind).missing]`). Cross-file inference of `data()` shapes is out of scope.
- **One unparsable or uncompilable `.pzl` does not abort the run** — it is its own positioned diagnostic and every other file still checks. The emitter runs the build's codegen, so a template that reads `event` as data and also uses the DOM `event` in a handler (DOC-SPEC-TEMPLATE §5) is an error here too.

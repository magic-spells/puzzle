# `puzzle add theme <name…>` — brief

Date 2026-09-18. Ships in 0.8.0 alongside the themes work (PR #137). Cory: "lets plan it
out and add it to 0.8.0 while we have that release still being worked on."

## Why

PR #137 makes `@magic-spells/puzzle-pieces` ship four palette files
(`registry/theme/{pieces,dim,warm,void}.css`) and lists them in `registry.json` under
`themes` with `modes: [light, medium, dark]`. The CLI still only knows the single default
`theme` (copied as `app/styles/pieces.css` by `puzzle add piece`); the other three are
unreachable from the CLI, which is how Sites and Pyramid ended up hand-copying and
drifting. This closes the loop for copy-in apps.

## Behaviour

`puzzle add theme <name…>` (one or more names; `--registry` and `--overwrite` as for
`piece`):

1. Read the registry manifest; `Registry` gains `Themes []Theme{Name, File, Label,
   Description}` and `Modes []string`. `Theme.File` goes through
   `validateManifestPath` like `Registry.Theme` does today (traversal defence).
2. Resolve each name (case-sensitive, exact). Unknown → error naming the available
   themes; nothing is written when any name is unknown (plan first, then write — same
   as `piece`).
3. `default` (or whatever entry's `file` equals `Registry.Theme`) IS the existing
   default-theme path: reuse `planTheme` exactly (destination `app/styles/pieces.css`,
   marker detection, lock key `theme/pieces.css`, the existing advisory). `puzzle add
   theme default` and `puzzle add piece` must stay idempotent with each other.
4. Any other theme → `app/styles/themes/<name>.css`, copied verbatim, locked as a unit
   keyed by its registry path (`theme/dim.css`), same lock shape as the default.
   Already-installed rules, mirroring pieces: file exists and hash matches lock → "up
   to date", skip; file exists and differs → refuse unless `--overwrite`; symlinked
   destination → refuse as `piece` does.
5. "Wired" detection: if `app/styles/styles.css` contains
   `@import "@magic-spells/puzzle-pieces/themes/<name>.css"` (either quote style) the
   theme is already provided by the package import — report that and skip the copy.
   ALSO extend the default's `planTheme` state (a): an import of
   `@magic-spells/puzzle-pieces/themes/default.css` counts as wired, so `puzzle add
   piece` stops copying `pieces.css` into apps that import the package.
6. Next-steps output (the D3 "print the manual line" convention): for each copied
   theme, `add \`@import './themes/<name>.css';\` to app/styles/styles.css (after
   \`@import './pieces.css';\`)` and one line: `switch with data-scheme="<name>" on
   <html>; modes: data-theme="light|medium|dark"`. Print once, deduplicated.
7. `puzzle add theme` with no name: list the registry's themes (name, label,
   description) with install state per theme (`installed` / `wired via package` /
   `—`), exit 0. Same for an unknown name's error listing.
8. `puzzle add` usage text / `puzzle --help` gain the subcommand.

Non-goals: no `puzzle update theme`, no removal, no rewriting `styles.css` for the
user (D3), no change to the fetcher (it already resolves the CLI's major.minor to
the newest pieces release), no change to the theme files or `registry.json` (they are
PR #137's).

the existing fake fetcher/registry helpers:

  symlinked destination
